## E: 進捗のJSON書き出し・読み込み

すべて利用者の端末のブラウザ内で完結します。

- **書き出し**: ボタンを押すと、ブラウザの `localStorage` にある進捗(回ごとの解答、選択、現在の問番号、チェック)をJSONにまとめ、端末のダウンロードとして保存します。保存先は利用者の「ダウンロード」フォルダなどで、アプリが任意の場所へ書き込むわけではありません。
- **読み込み**: 利用者がそのJSONファイルを選ぶと、ブラウザがその場で読み取り、`localStorage` に戻します。
- **サーバ**: GitHub Pages は静的な配信だけなので、サーバへの送信も保存もありません。

用途は、ブラウザのデータを消したときの復旧、端末の買い替え、PCと携帯の間の手動での引き継ぎです。参照元は「アカウントや端末間の同期はしない」と決めていました。Eは自動同期ではなく、利用者が手でファイルを持ち運ぶ機能です。その決定とは矛盾しませんが、不要なら見送って構いません。

## ハッシュルーティングへの変更

「URLのどの部分でどの画面を決めるか」を変えるものです。画面の見た目や操作は変わりません。

| | 参照元(パス方式) | 変更案(ハッシュ方式) |
| --- | --- | --- |
| 回一覧 | `/system-arch-training/` | `/project-manager-training/` |
| 演習画面 | `/system-arch-training/2025-r07-haru/` | `/project-manager-training/#/2025-r07-aki` |

**パス方式の問題**

- GitHub Pages はファイルを探して返すだけの仕組みです。`/2025-r07-haru/` というファイルは実在しないため、そのURLを直接開いたり再読み込みしたりすると 404 になります。
- 参照元は、ビルド時に `index.html` を `404.html` としても複製し、404のときにアプリを開かせて回避していました。`vite.config.ts` の `closeBundle` に、そのための処理があります。

**ハッシュ方式の仕組み**

- `#` より後ろはブラウザが解釈するだけで、サーバには送られません。どのURLでも、サーバが返すのは `index.html` だけです。
- そのため 404 の細工は不要になります。再読み込みや、戻る・進むも問題なく動きます。

**変更内容**

- `route.ts`(87行)のURL解釈を、`location.pathname` から `location.hash` に変えます。
- `hashchange` イベントを購読します。
- `vite.config.ts` から 404.html の複製処理を除きます。
- 「存在しないidなら、その回がない旨を出して一覧へ戻す」という挙動は、そのまま維持します。

**デメリットとトレードオフ**

- URLに `#/` が入ります。
- 問題番号をURLに入れない方針(問の移動ではURLを変えない)は、そのまま保ちます。
- 公開後にURL形式を変えると既存のブックマークが切れるので、決めるなら最初です。

ただし、この変更は必須ではありません。参照元の方式でも問題なく動いています。コードを数十行と1つの設定処理だけ減らせる、という程度の改善です。
